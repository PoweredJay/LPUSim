# Architecture

How the compiler, scheduler and cycle simulator fit together. Numbers that come out of a run are in
`results/REPORT.md` (generated by `make`); this file describes the model, not its results.

Tags: **[P]** published (ISCA 2020 paper or patent US 11,360,934), **[I]** inferred from the paper,
**[A]** assumed, **[Ours]** a design choice of this project. Latency values live in
`planning/instruction-timing-table.xlsx`.

## 1. Data flow

```
model.cpp      build_resnet(depth)  -> Net (layers, random int8 weights)
               golden(net, image)   -> reference int8 activations / int32 logits, and the
                                       per-layer requantize constants (Ma, Mr, S)
compiler.cpp   Compiler(net, sim, sch, fp).compile()
                 - picks a layout for every tensor, allocates MEM, writes the weights, gather maps
                   and input straight into sim.mem() (the initial MEM image)
                 - lowers each layer into pipelines and hands them to the scheduler in order
sched.cpp      Scheduler::place(pipeline) -> start cycle; reserves every resource it uses
ifetch.cpp     build_program()      -> Scheduler::emit() per-IQ programs, then plans Ifetch refills
                                       so each program fits its 640 B IQ, and writes the text into MEM
lpusim.cpp     Simulator::run(program) -> executes every IQ cycle by cycle and checks every rule
main_resnet    compares the logits in sim.mem() with golden(); report.cpp writes results/
```

The compiler never names a cycle, a stream id or a VXM ALU. The scheduler picks those; the
simulator checks the scheduler's choices independently.

## 2. Machine model (`lpusim.h`, `modules_full.h`)

* **Floorplan [I].** One row of positions, west to east: MXM_W (0), SXM_W (4 positions),
  MEM_W43..W0 (5-48), VXM (49), MEM_E0..E43 (50-93), SXM_E, MXM_E (98). MEM index 0 sits next to the
  VXM. A stream moves one position per cycle [P], so distance is latency.
* **Vectors and streams [P].** A vector is 320 bytes (20 superlanes x 16 lanes). Each direction has
  32 streams. int32 data uses 4 consecutive streams (one byte plane each); an LW uses 16.
* **MEM [P/A].** 88 slices x 8,192 words of 320 B, 2 banks per slice (address bit 12) [A]. One read
  port and one write port per slice; a read and a write to the same bank in one cycle is illegal
  (pseudo-dual-port).
* **MXM [P/I].** 4 planes (W0, W1, E0, E1), each a 320 x 320 int8 weight array. LW streams a tile
  into the plane's buffer (20 issues x 16 streams = 320 rows), IW copies buffer -> array in 1 cycle
  [A], ABC multiplies one activation vector per issue with d_func 20 [I], emitting 4 int32 byte
  planes.
* **VXM [P/A].** 16 ALUs, each with its own IQ: add, mul by an immediate, convert (round, shift,
  saturate), relu, max.
* **SXM.** 28 IQs exist; no SXM op is executed yet (the lowering needs none).
* **IQs and issue channels [P/Ours].** 144 IQs, numbered in column order. Every IQ has "ways":
  independent instruction threads. A MEM IQ has an R-type way (Read, Gather) and a W-type way
  (Write), every IQ has a fetch way (Ifetch). The scheduler reserves *channels* = (IQ, way): 232
  issue channels plus 144 fetch channels.
* **Latency.** T = N + d_func + delta [P]: an op issued at position p in cycle t has its result on
  the stream register at p in cycle t + d_func, and it reaches position p' after |p' - p| more
  cycles. Defaults are in `LatencyTable`; `load_csv()` overrides any cell with a number.

## 3. Stream registers and tags (`DiagStreams`)

A value written going East at position q in cycle t is at position p in cycle t + 1 + (p - q), so
t + 1 - q is constant along its path (its "diagonal"); going West, t + 1 + q is. The simulator
stores, per (direction, stream, diagonal), the list of writers, and a read at (p, T) returns the
nearest upstream writer on that diagonal. This is exact (test 0 compares it with the copy-every-
register `StreamRegisterFile` in `modules_full.h`) and O(1) per access.

Every value carries a tag (edge id, vector index) and every operand states the tag it expects, so a
read that sees the wrong vector, or nothing, is reported. This checks the schedule's timing, not just
the final answer.

## 4. Scheduler (`sched.h/.cpp`)

* **Pipelines.** A pipeline is a set of ops joined by stream edges, e.g. Read -> Gather -> ABC ->
  VXM chain -> Write. Streams cannot buffer, so every edge fixes a timing relation [P Eq. 4]:
  phase(consumer) + d_skew = phase(producer) + d_func + hops. The scheduler solves these once
  per pipeline; vector m of an op issues at S + phase + m.
* **Placement.** Pipelines are placed in program order at the earliest start S that is free in
  (1) the busy intervals of every issue channel, (2) MEM bank read and write intervals, (3) the 16
  VXM ALUs, (4) stream registers, as rectangles in (diagonal x position) space per stream and
  direction, and (5) per-word MEM dependencies (RAW, WAR, WAW), so a consumer can stream a tensor
  while its producer is still writing it. Per-op lower bounds from the compiler keep each MXM
  plane's LW -> IW -> ABC order.
* **Emission.** `emit()` writes one entry list per channel: the 35-cycle Sync preamble [P], NOPs
  for gaps (split at 65,535, a 16-bit field [P]), each instruction, and Repeat n-1 for runs.

## 5. Lowering (`compiler.h/.cpp`) [A unless noted]

* Activations are int8, one 320-byte word per pixel per 320-channel group. A tensor read by a 3x3
  conv is "dy-packed": its channel block is stored up to 3 times at different superlane offsets, so
  one per-superlane Gather (map vector -> one address per superlane) builds the taps of a row.
* A conv is a sum over K-vectors of [M x 320] x [320 x 320] tiles. Each round runs up to 4
  (tile, M-chunk) slots on the 4 planes in one rigid pipeline. The VXM sums the plane outputs;
  int32 partial sums that span rounds ping-pong between two MEM banks near the VXM.
* Requantize in the VXM: y = relu(sat8((acc * Ma + res * Mr + 2^(S-1)) >> S)).
* Weights: each 320 x 320 tile is 16 slices x 20 words. Weight tiles get their own slices
  (default MEM28-43 on each side, `CompileOptions::weight_index_lo/hi`), so an activation stream
  never holds the read port the next LW needs. The two planes of a hemisphere load from the same
  16 slices, so their LWs serialize; the roofline report shows what that costs at low load.
* Tensors read by several planes at once are replicated (one read port per slice).
* conv1 runs as a 1x1 conv over a host-side im2col (147 channels). FC writes raw int32 logits.
* ResNet-101/152 weights do not fit with this lowering (tiles are padded to 320 x 320); with
  `--alias-weights` the overflow tiles reuse earlier tiles' slices: same ports and banks, wrong
  data, so those runs are timing-only projections.

## 6. Bounded instruction queues and Ifetch (`ifetch.h/.cpp`)

* Each IQ holds 640 bytes [P col. 12]. NOP = 1 byte, every other instruction 4 bytes [P col. 10;
  encoding Ours: byte 0 opcode, bytes 1-3 packed fields]. The first 640 bytes of each IQ are loaded
  before the Sync [Ours].
* The rest of each program is stored in MEM as constants [P col. 16], in never-used words, one
  320-byte text vector per word.
* A refill is Ifetch + Repeat 1: two text vectors, 640 B [P col. 12]. Bytes enter the IQ at 16 B
  per cycle [P]: chunk j of a vector fetched at cycle c lands at c + j, and the Repeat is 20 cycles
  after the Ifetch, so a 640 B refill takes 40 cycles [Ours].
* Each text vector is a pipeline (MEM Read of one word -> stream -> Ifetch on the IQ's fetch way)
  that the scheduler places like any compute pipeline, so it reserves the read port, bank and
  streams. Refills are planned after the compute schedule, in deadline order, using only resources
  the compute left free, and never move a compute op.
* A refill must start late enough that every 16 B chunk has room when it lands and early enough that
  every instruction's chunk lands before it issues. The simulator re-checks both per chunk after
  the run (`Simulator::check_text`): underflow (an instruction issues before its bytes arrived,
  patent col. 13) and overflow (more than 640 B in the IQ), and checks that every Ifetch delivers
  the IQ's next bytes in order with the right contents.

## 7. Simulator checks (`lpusim.cpp`)

`Simulator::run` advances an event heap of (next issue cycle, channel) and a 64-cycle ring of pending
stream writes. Every one of these is a violation, and every reported result has zero:

* an operand stream that is empty or holds a different tag than expected
* two writers on one stream register in one cycle
* a read and a write to one MEM bank in one cycle
* an opcode on an IQ or way that cannot execute it
* more than one R-type or one W-type instruction from a MEM IQ in a cycle (`--mem-single-issue`:
  more than one in total), or more than one instruction from any other IQ
* IQ underflow or overflow, and out-of-order or wrong Ifetch bytes

The simulator never stalls. A schedule that is one cycle off is reported, not absorbed.

Superlane stagger [P Fig. 6]: every op used is lane-local except the MXM reduction, whose d_func
already covers it, so superlane t is superlane 0 shifted by t cycles. The simulator runs superlane-0
time and adds 19 cycles at the end.

## 8. Reproducing

`make` in the repo root runs `scripts/reproduce.sh`: xlsx -> CSV, build, tests, ResNet-50/101/152,
sensitivity runs, roofline sweeps, `scripts/plots.py`, `scripts/report.py`. Every number in the
README is in `results/REPORT.md`, which that last step computes from the run outputs.
